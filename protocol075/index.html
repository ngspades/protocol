Protocol 0.75 and 0.76

This page documents the Ace of Spades 0.75 protocol and its 0.76 variation, the classic wire public servers speak. It is written from the point of view of both ends: every packet says which direction it goes, what the server sends or expects, and what a client has to send.

0.76 differs in exactly three places, marked [0.76] throughout: the ENet connect data, the Map Start packet and the World Update entry. One implementation can speak both.

Where this comes from: the packets and rules below were written from ngspades-client and ngspades-server, then checked against the AoS 0.75.015 Canon Client Doc (version 0.0.3, and the earlier 0.0.2 draft) by not a burner (CC0, a client's view of the protocol), the API documentation of his server LSd (apidoc/), the original SpadesX (the server ours started from) and BetterSpades. Where they disagree the page says so. If you see an error, please open an issue.

Connection

Ace of Spades uses ENet 1.3 over UDP. When you connect, the 32-bit connect data picks the protocol:

NumberProtocol
30.75
40.76
ENetHost *host = enet_host_create(NULL, 1, 1, 0, 0);
enet_host_compress_with_range_coder(host);
ENetPeer *peer = enet_host_connect(host, &address, 1, 3);
SettingValue
Port32887 by convention
Channels1 (channel 0)
CompressionENet's range coder, mandatory in both directions
Reliabilityeverything reliable except World Update (2), sent unreliable
Framingone game packet per ENet packet: one Uint8 id, then the payload

A server must check the length of every packet before reading it, and check the player_id field of a client packet against the sender's id.

A server may send the map again in the middle of a match (a new round); a client must handle Map Start at any time.

Disconnect Reasons

The server puts a Uint32 reason in the ENet disconnect event. ENet also uses 0 for a timeout, so 0 is ambiguous.

NumberReasonNotes
0Timeoutor an unspecified server reason
1Banned
2Kickedpiqueserver and BetterSpades read it as "too many connections" instead (the quirk SCREWED_DISCONNECT_DATA)
3Wrong protocol versionconnect data was not 3 or 4
4Server full
5Server shutting down
8, 9, 10, 11Banned, full, kicked, wrong versionthe same reasons once the player is in the game. Historically 0..4 were sent during the map transfer and 8..11 after it, because the Voxlap client uses the code during the transfer as an index into its language strings. OpenSpades only knows 10 (kicked) there
20Invalid name
61Server shutting downan alternative value some servers use

A system Chat Message from player 255 sent just before the disconnect is the kick text (the Kick Reason extension, see Extensions). Show any unknown number as "unknown"; never index a table with it. A code outside the list is handled as unknown, and a client must not crash on it.

About Addresses

aos://<address>[:<port>][<version suffix>]
  • <address> is the IPv4 address as one decimal number in little-endian byte order: aos://16777343 is 127.0.0.1 (0x0100007F). Byte 0 of the address is the low byte of the number.
  • <address> ranges from 1 to 4294967295 and <port> from 1 to 65535. A value outside the range is not an address.
  • <port> defaults to 32887.
  • A suffix after the port (:0.75, /0.76) names a version. An unknown suffix means 0.75.

Accept a dotted address (aos://1.2.3.4:32887) and a bare host:port too.

About Coordinates

The map is 512 x 512 x 64 voxels. x goes east, y goes south, and z grows downwards: 0 is the top of the world, 63 is the bottom (water) layer.

  • A float position (0,0,0) is the corner of voxel (0,0,0); (0.5,0.5,0.5) is its centre. Floor each axis to get the voxel.
  • A player's position is its eye, not its feet.
  • Servers do not let a player dig or build at z = 62 and z = 63. A client still applies what it receives: only the spade-3 and grenade block actions (2 and 3) leave z >= 62 alone.
  • Terrain outside 0..511 on x/y is drawn as a copy of the map (toroidal wrap). Players, block edits and block physics do not wrap; grenades do.
  • A look direction is the unit vector (ox, oy, oz); oz is negative when looking up (because z grows downwards).

If your engine has y up, convert at the protocol boundary: engine = (x, 63 - z, y), and back with (x, z, 63 - y).

About Text

  • CP437 is the original encoding. Bytes 0x80..0xFF are code page 437.
  • UTF-8 is sent by newer servers: a string beginning with byte 0xFF and valid UTF-8 after it is UTF-8 (drop the 0xFF). Anything else is CP437. To send, use CP437 when every character fits, otherwise 0xFF + UTF-8 — and only to a server known to read it (its extended version answer's feature bit 0, or a 0xFF line it wrote).

Chat text may contain colour control bytes: 0x01-0x02 team colours, 0x03 spectators, 0x04 red, 0x05 green, 0x06 white, 0x07 grey, 0x08 yellow. \n and \r break the line.

On the wire, 0x01-0x07 are the colour bytes real servers send, in both encodings; 0x08 (yellow) belongs to the UTF-8 variant of the text (the one that begins with 0xFF), so a CP437 string from a server that does not speak UTF-8 does not carry it. A reader should treat every other byte below 0x20 as having no colour meaning. This describes what travels, not what any particular client draws.

In the UTF-8 variant the bytes 0x09-0x1F are replaced by the replacement character U+FFFD, and \n and \r both break the line. In the CP437 variant 0x01-0x1F are the symbols of the code page (☺ ☻ ♥ ♦ ♣ ♠ and so on). A NUL ends the string in both. Two other variants exist in the wild and are named by quirks: OpenSpades' own CP437 table, and an ASCII-only one that drops every other byte (see Quirks).

Position Data

Server -> Client

Teleports or corrects the receiver. It carries no player id: it is always about you.

InfoValue
Packet ID0
Total size13 bytes
Field NameField TypeNotes
X, Y, ZVec3the eye position

The client sets its position at once and keeps its look. Never interpolate: it is a correction, not a movement.

Client -> Server uses the same packet to report its eye position, reliably, about once a second while alive (do not depend on exactly 1 Hz as a server) and right after a teleport. The server compares it with its simulation and answers with Position Data when it disagrees.

Orientation Data

Server -> Client

Turns the receiver to a direction. Rare; normally the look rides World Update.

InfoValue
Packet ID1
Total size13 bytes
Field NameField TypeNotes
X, Y, ZVec3unit look vector

Client -> Server: the client's look, sent whenever it changed, at most about 120 times a second, and right before each shot so the server can validate the hit. Compare for exact equality with the last value sent: a threshold ("only when it moved enough") leaves the server with a stale look.

World Update

Server -> Client

The only unreliable packet. A newer update replaces the old one.

InfoValue
Packet ID2
Total size1 + 24 * n (0.76: 1 + 25 * n)

0.75: one entry per player slot, indexed by id, up to 256 slots.

Field NameField TypeNotes
PositionVec3eye position, (0,0,0) = not visible
OrientationVec3look vector

[0.76] one entry per present player:

Field NameField TypeNotes
Player IDUint8
PositionVec3
OrientationVec3

Skip your own entry. A zero position means "not visible": keep the last known position. Servers fill dead players, players out of the fog and free slots with zeros. Interpolate between updates (about 60 a second).

Existing Player

Client <-> Server

A player already in the match (server to client), or the client's join (client to server).

InfoValue
Packet ID9
Total size12 + name (the NUL is part of the name), so at least 13
Field NameField TypeNotes
Player IDUint8client to server: ignored, the sender is the connection
TeamInt80 team 1, 1 team 2, -1 (255 on the wire) spectator
WeaponUint80 rifle, 1 SMG, 2 shotgun
ToolUint8as in Set Tool
KillsInt32the score. Overflow wraps
ColorColorB, G, R
NameCP437 Stringat least 15 characters must be readable, cut on a character boundary

A server sends it for every other player after the map and before State Data. It carries no position: keep the player hidden until a World Update or Create Player places them.

A client sends it after State Data to join, with the chosen team, weapon, tool (gun), zero kills, its block colour and its name. The Player ID it writes is not trusted (SpadesX skips it: a client "always sends a dumb id", and the server's receive_existing_player only accepts it from a spectator). The server answers with Create Player.

A joined player's position is not in the packet: the usual place for the hidden player is far out of the map, for example (256, 256, 1024) in the packet's coordinates, and its orientation is the spawn orientation of its team. Its inputs start at zero.

The extended version answer reuses this id: the first byte after the id is 'x' (0x78), which no player id can be (see Extensions).

Short Player Data

Client -> Server — joining from the spectators

Not an older form of Existing Player. A player who is already named, and is a spectator, picks a team and a weapon with it. There is no name in the packet (the clidoc calls it "join from spectator" in 0.0.2 and "spectator switch" in 0.0.3, which adds that a player who is not spectating uses Change Team and Change Weapon).

InfoValue
Packet ID10
Total size4 bytes
Field NameField TypeNotes
Player IDUint8ignored, the sender is the connection
TeamInt80 or 1, 255 spectator. Anything else becomes spectator
WeaponUint80 rifle, 1 SMG, 2 shotgun

A server reads it only from a connection that is currently a spectator (SpadesX and ours drop it otherwise: a player already in a team uses Change Team and Change Weapon). It keeps the name the player gave in its Existing Player. The server then spawns the player and answers with Create Player.

The first thing a client sends to join is Existing Player, which carries the name. A server that treats Short Player Data as a first join has no name to use. The author of LSd reports that the original Voxlap server does accept it that way, and then shows uninitialised memory as the player's name. A client should join with Existing Player, and a server should not accept this packet from a connection that has not sent one.

A client with the quirk NOSHORTPLAYER never sends it and uses Change Team and Change Weapon instead (see Quirks). The packet is never sent by a server, and a client that receives one logs it and carries on.

Move Object

Server -> Client

InfoValue
Packet ID11
Total size15 bytes
Field NameField TypeNotes
ObjectUint8CTF: 0/1 intels, 2/3 tents. TC: territory index
TeamInt8the owner, for TC
PositionVec3the new cell

CTF: moving an intel also drops it from its carrier, silently. TC: team is 0 or 1, or neutral. Servers send neutral as 2 (pyspades and piqueserver do; our server's 0.75 profile has no TC, so it never sends one). A client should read any value other than 0 or 1 as neutral in territory and object packets, and as spectator (-1) in every packet that names a player's team. Some drafts treat 2 as a "neutral spectator" and 3 as neutral; the rule above covers both.

Create Player

Server -> Client

A player spawned (or joined for the first time).

InfoValue
Packet ID12
Total size15 + name (16 with an empty name)
Field NameField TypeNotes
Player IDUint8
WeaponUint8
TeamInt8spectator = not alive
PositionVec3the eye
NameCP437 Stringabsent in a 16-byte packet

The player is alive unless the team is spectator. It faces east for team 1 and west for team 2. Reset its block colour to (111,111,111) and restock it (full health, 50 blocks, 3 grenades, full magazine and reserve).

A 16-byte packet has no name: keep the one you had (a player not yet joined gets an empty one), and a longer packet sets the name.

The offset applied to z is where the sources differ. The original Voxlap client and LSd's default are z - 2; the clidoc's 0.0.2 draft said z - 2, its 0.0.3 says z - 2.4, which LSd names the quirk INSKY; and INFLOOR uses z as it is. ngspades-server sends the eye position and ngspades-client uses it as given (INFLOOR). A server that does not know which a client implements sees a player a little too high or too low for a moment. See Quirks.

Block Action

Client <-> Server

InfoValue
Packet ID13
Total size15 bytes
Field NameField TypeNotes
Player IDUint8
ActionUint8see below
X, Y, ZVec3ithe block cell
ActionEffect
0build one block with the player's colour (a repaint when already solid)
1destroy one block
2spade: destroy the block and the ones above and below (1 x 1 x 3)
3grenade: destroy 3 x 3 x 3, silently
4destroy one block (a gun)
5destroy one block (a spade)

Actions 2 and 3 leave z >= 62 alone; cells outside the map are ignored.

A value of Action not in the table is ignored. For the client's own block count (the HUD, the server counts for the rules): a build (0) costs one when you have more than one block, a destroy (1) gives one back only while holding the spade and below 50, and 5 gives one back below 50. Actions 4 and 5 are later additions of the same two destroys.

A server applies its rules (tool in hand, no sprinting, reach about 4 blocks, a solid neighbour for a build, the block count, editable cells) and relays it to everyone. A client batches edits that arrive together: keys by position (last wins), apply creates then destroys, then run block physics once. Applying them one by one makes a repaint collapse a structure.

Block Line

Client <-> Server

InfoValue
Packet ID14
Total size26 bytes
Field NameField TypeNotes
Player IDUint8
StartVec3i
EndVec3i

Builds a line of blocks between the two cells with pyspades' modified DDA (not a ray cast: cube_line, not cast_ray), skipping cells that are already solid and drawing every cell in full whatever the length. The line always has |dx| + |dy| + |dz| + 1 cells, the already-solid ones included. It costs that many blocks. A client with fewer blocks than that does not send it. The edits are batched like a Block Action (see below).

Quirks

Quirks are switches in how a client and a server read the protocol: places where implementations disagree. The clidoc numbers the first seven and LSd's API names nine. A client that tells the server which ones it has implemented (and none that it has not fully implemented) lets the server make better choices. LSd also guesses them for clients that do not say (is_quirk_heuristic). The wire format of the announcement is not documented anywhere; ngspades does not send one.

NumberNameEffect

Game Rules

The wire carries state; the game still needs these rules.

Players

Ids 0..255. Keep state for all 256: joined, alive, team, weapon, tool, score, name, block colour, position, orientation, input. Only for yourself: health, blocks, grenades, magazine, reserve. Out-of-range values fall back to something safe (spectator, rifle, spade); never index a table with a value from the wire.

Fog

Sight is a cylinder of radius 128 around the camera. Nothing beyond is drawn, shots stop there, the sky is the fog colour. State Data and Fog Color set the colour. A server may send positions beyond the fog anyway; do not draw them (that is a wallhack).

Block Physics

When a voxel stops being solid, check its six neighbours. Each solid one starts a flood fill through solid voxels. If the fill reaches z >= 62, nothing happens; otherwise everything it reached is detached, falls and is removed. Voxels that were already empty inside a spade or grenade area must not start a check.

Damage, Death and Respawn

The client reports hits; the server sends Set HP, then Kill Action at 0. On death the intel is dropped (Intel Drop), the corpse is drawn (or a grave), the kill feed updates and the respawn counter runs from the kill packet. The server spawns the player with Create Player.

Blocks

A player carries at most 50 blocks. A build costs one, a spade destroy gives one back. Restock refills at the tent. The client counts locally for the HUD; the server counts for the rules.

Weapons

What pyspades and SpadesX do (ngspades-server's 0.75 profile too). The wire does not carry any of it: the server applies it and tells the client the result with Set HP, Kill Action, Weapon Reload and Restock.

A spade hit does 80. A player starts with 100 health, 50 blocks and 3 grenades, and Restock restores them. The server counts: a client only reports hits (the hit type is in Hit: 0 torso, 1 head, 2 arms, 3 legs, 4 melee).

A grenade does damage to every player within 16 blocks on each axis who is in line of sight of it, 4096 / d^2 with d the distance, at most 100, and only above z = 62. It destroys a 3 x 3 x 3 block volume with the silent block action. LSd documents a different formula, so two servers can disagree.

A landing at a downward speed above 0.24 (the physics' own unit) halves the horizontal speed and plays the fall sound. Above 0.58 it also hurts, by (speed - 0.58)^2 * 4096 health, sent as a Set HP of type 0 with no source. SpadesX also lets a player restock at its tent at most every 15 seconds and counts a capture only if 5 seconds have passed since the player was last in its tent. These are server rules, not protocol.

CTF

Two scores, a capture limit, two intels (held by a player or lying at a cell), two tents. Touching the enemy intel picks it up, carrying it into your tent captures it, dying drops it. A capture puts the intel back at its base (Move Object). A round ends at the capture limit.

TC

A list of territories (position and owner). Standing in one moves its capture towards your team; the server sends Progress Bar and then Territory Capture. Owning them all wins.

Writing a Server

Must

  1. An ENet host with the range coder, accepting connect data 3 (and 4).
  2. Version, ban and capacity checks with the right disconnect reasons.
  3. The map: VXL, zlib, Map Start, Map Chunk.
  4. Existing Player for every player, then State Data, after the map.
  5. The join: Existing Player from a connection that has not joined (its name is in the packet), then Create Player to everyone. A spectator joins a team with Short Player Data or Change Team, and only a spectator may.
  6. World Update at a steady rate, unreliable, zeros for unseen slots.
  7. Relay and validate Input Data, Weapon Input, Set Tool, Set Color, Orientation Data, Position Data.
  8. Hit -> Set HP -> Kill Action -> respawn.
  9. Block Action and Block Line with validation, block physics, Restock.
  10. Chat and Player Left.
  11. At least CTF.

Should

  • Server-side movement physics with corrections.
  • Create Player for players that do not move (bots) when someone joins, or they stand at the map corner until the next World Update.
  • Grenades simulated on the server.
  • Version Get / Handshake Init, as optional checks.
  • 0xFF + UTF-8 for text CP437 cannot express.
  • Ext Info and the extensions.

Spawn a player with 100 health, 50 blocks, 3 grenades, a full magazine and reserve, the gun in hand and no input held. Send every packet reliable except World Update, and one game packet per ENet packet.
