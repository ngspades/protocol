Protocol 1.0

This page documents protocol 1.0, the protocol of the Shoot and Destroy server. It starts from OpenSpades' abandoned ngspades branch ("WorldOfSpades 0.1"), with that reference's defects fixed and the packets a whole game needs added: chat, building, damage and game modes.

Current revision: 1.3 (three weapon slots, the compact player trajectory, the jetpack bits). The revision is informational; nothing is negotiated on it. There is no backward compatibility inside 1.0 yet: a wire change updates both ends together.

Connection

1.0 uses ENet 1.3 over UDP (IPv4 and IPv6), and WebRTC DataChannels in a browser. The 32-bit connect data picks the protocol:

NumberProtocol
135272729 (0x08101919)1.0
ENetHost *host = enet_host_create(NULL, 1, 2, 0, 0);
enet_host_compress_with_range_coder(host);
ENetPeer *peer = enet_host_connect(host, &address, 2, 0x08101919);
SettingValue
Port32887 by convention, the same as 0.75
Channels2: channel 0 reliable for everything, channel 1 unreliable sequenced for movement
CompressionENet's range coder, mandatory
Framingone game packet per ENet packet: one Uint8 id, then the payload

A client sends its own body (Client Side Entity Update, and an Entity Update carrying only a trajectory) on channel 1 unreliable. Everything else is reliable on channel 0. An update that must be seen before an action — right before a Hit Entity or a block build/dig — goes reliable on channel 0, or the server does not yet know you are firing or holding the right tool and refuses the action.

A server answers a vanilla server's connect data with reason 3 ("wrong protocol") and no Kick; treat that as "not a 1.0 server" and reconnect with connect data 3.

WebRTC (browsers)

A browser cannot send UDP. It reaches our servers over WebRTC DataChannels; the packets are identical, only the carrier changes. Signalling goes through our master (Master Server).

  • Two DataChannels, created before the offer: reliable (defaults) is channel 0, unreliable ({ordered: false, maxRetransmits: 0}) is channel 1. Any other label is closed by the server.
  • A text message is control. After both channels are open, send connect 135272729 on reliable (the connect data in decimal). Anything else is refused with ENet's refusal (3 = wrong protocol).
  • A binary message is exactly one 1.0 packet, at most 16 KB.
  • The server ends a connection with the text disconnect <reason>, then closes the peer. A binary message before connect is dropped.

Disconnect Reasons

NumberReasonNotes
0Unknown
1Internal server error
2Server full
3Kickeda Kick packet with the text came first
4Server stopped
5Timeouta handshake step took too long
6Malformed packet
7Protocol mismatchthe protocol name was not ours

Vanilla uses the same field with another table (1 banned, 2 connection limit, 3 wrong protocol). The meaning depends on the protocol the connection was opened with. The ambiguous case: connecting with the 1.0 magic to a vanilla server gives 3 with no Kick.

Timeouts

The server drops a connection that does not advance: 10 s for Initiate Connection, 10 s for the certificate, 300 s for the map transfer. There is no timeout in the game; ENet's peer timeout applies.

Handshake

client                                            server
  ENet connect (0x08101919) or WebRTC "connect" -->
             <-------------------------------- Greeting (1)
  Initiate Connection (2) ------------------------>
             <------------------------ Server Certificate (3)
  Client Certificate (4) ------------------------->
             <------------------------ Game State Header (6)
             <------------------------ Map Data (7) x N
             <------------------------ Map Data Final (11)
  Map Data Acknowledge (10) ---------------------->  (after decoding)
             <------------------------ Game State Final (8)
  Generic Command "join <team> <weapon>" --------->
             <------------------------ Generic Command "local-player <id>"
             <------------------------ Entity Update / Player Update / Terrain Update

A world change (a new round, a reset) restarts the transfer at Game State Header for every connection. The player is removed and the client has to join again. Packets still in flight are dropped, not a protocol error.

Packets

All packets start with an unsigned byte naming their type. Unknown ids are ignored, not a reason to disconnect.

Data Types

All multi-byte fixed-width values are little-endian.

ShorthandDetails
Uint8, Uint16, Uint32fixed width
Float32-bit IEEE-754
Vec3three Floats
Varintunsigned LEB128, at most 10 bytes
Svarintzigzag, then Varint
BytesVarint length, then raw bytes (at most 1 MiB)
StringBytes of UTF-8, no NUL inside
Maprepeated String key, String value, ended by an empty key
Colorthree bytes in the order B, G, R
Block CoordSvarint x, Svarint y, Svarint z

Varint examples: 0 -> 00, 127 -> 7F, 128 -> 80 01, 300 -> AC 02. Zigzag examples: 0 -> 00, -1 -> 01, 1 -> 02, -2 -> 03.

A decoder must reject a truncated packet, a varint over 10 bytes, a string over 1 MiB or with a NUL in it, a mask bit it does not know, and an out-of-range enum. Mask bits are not self-describing: an unknown bit's payload cannot be measured, so new mask bits and new trailing fields change both ends together.

Greeting

Server -> Client

InfoValue
Packet ID1
Total size1 + 1 + 5 + 1 + 2 + 128
Field NameField TypeNotes
MagicStringalways "Hello"

Hex: 01 05 48 65 6C 6C 6F 80 01 <128 bytes>.

The nonce is used by the connect token. A client that receives any other packet id before the Greeting must treat the server as not 1.0 (about 1 in 50 public 0.75 servers accept the magic and then speak 0.75).

Map cache. A client that already holds the stream answers with Generic Command "map-cached 1"; the server then sends no Map Data at all and goes straight to Map Data Final. Map Data / Map Data Final

Server -> Client

InfoValue
Packet IDs7 (Map Data), 11 (Map Data Final, empty)
Total size1 + n / 1
Field NameField TypeNotes
FragmentBytesone piece of the stream, in order

Append every fragment; the concatenation is one stream. Map Data Final ends it. Decode the map, apply the Terrain Updates that arrived during the transfer in order, then acknowledge. The server keeps broadcasting terrain edits to loading connections, so keep them until the map is ready.

Map Formats

vxl is the zlib-compressed VXL, exactly the bytes 0.75 sends in Map Chunk. One loader serves both protocols.

ngmap is a zlib stream (2-byte header, Adler-32 trailer). Decompressed:

Field NameField TypeNotes
SignatureUint320x1145148A
WidthUint16
HeightUint16
DepthUint16at most 64
QualityUint81..100
Geometrycolumn entriesone per column, boustrophedon: y 0..h-1, x 0..w-1 on even y, w-1..0 on odd y
JPEG LengthUint32
JPEGUint8 arraythe lossy colour tiles
Colour Blocksto the end

A column entry is a format byte then either a run-length list of Uint8 toggle positions (the first byte carries 0x80 when the column starts solid at z 0, the last byte is always depth) or a bitmap of 16-voxel slices. Colours are cut into 8x8x8 cells with one of six formats (constant, linear, planar, volumetric; raw or interpolated, some in JPEG tiles).

Do not re-implement ngmap from this summary. Port GameMap_ngmap.cpp from the ngspades reference (about 1,900 lines) or ship the C++ codec behind a C interface. It needs zlib and a JPEG decoder. Use Map Quality = 0 and skip it entirely if your client only needs to work.

Entity Update

Server -> Client

InfoValue
Packet ID30
Total sizevariable
Field NameField TypeNotes
ForcedUint81 = apply even to entities this client owns
ItemsEntity Update Item x nto the end of the packet

An update is a delta: keep the last value of each part and change only what the mask announces. An item with mask == 0 is never sent. An item for an unknown id without Create is ignored.

A client ignores parts for entities it owns, unless Forced is set or the item has Create: that is how the server corrects a client it disagrees with.

Client Side Entity Update

Client -> Server

InfoValue
Packet ID35
Total sizevariable
Field NameField TypeNotes
ItemsEntity Update Item x nto the end; never with Create

You report your own body: trajectory, input when it changed, tool, block colour. Movement is client-authoritative, but the server checks it:

  • items for entities you do not own are dropped;
  • a change of trajectory type is refused and corrected;
  • the new position must be within 0.1 block of the server's extrapolation along the old velocity, and the velocity within 0.1, or the server sends a forced correction.

Send at a steady rate (30 Hz), unreliable on channel 1, with the input whenever it changed; one reliably on channel 0 right before a hit or a block edit.

Terrain Update

Server -> Client

InfoValue
Packet ID40
Total sizevariable

A list of edits to the end of the packet, as deltas from a cursor that starts at (0,0,0):

Field NameField TypeNotes
DXInt8if -128 (0x80): the cursor moves — read CX, CY, CZ, then DX again
DYInt8
DZInt8
HealthUint80 = destroyed, otherwise created
Red, Green, BlueUint8 x 3only when created; R, G, B here
Create TypeUint8only when created: 0 unspecified, 1 player
Destroy TypeUint8only when destroyed: 0 unspecified, 1 damage, 2 collapse

The absolute cursor fields are unsigned Varints. The cursor does not follow the edits: deltas are always relative to the last explicit cursor.

Example: create an orange block (255,128,0) at (10,20,30), health 100, by a player:

28  0A 14 1E  64  FF 80 00  01

Destroy the block at (300,5,63); x does not fit, so the cursor moves first:

28  80 AC 02 05 3F  00 00 00  00  01

A create with health below 100 is a cracked block. Cells marked Collapse are falling structures: remove them and build the falling piece from their colours and connections. Apply a whole packet, then run block physics once.

Game Mode State

Server -> Client

InfoValue
Packet ID80
Total sizevariable
Field NameField TypeNotes
StateMapkey/value strings

A packet whose first entry is mode is a snapshot: forget all game mode state, then apply. Any other packet is a delta: each key replaces its value, an empty value removes it. A snapshot comes right after Game State Final and at every round start; a delta whenever something changes.

Numbers are decimal, lists comma-separated with no spaces, positions are block cells.

KeyValueMeaning

Extrapolate a territory as permille + rate * elapsed, clamped to 0..1000.

The objectives are entities: each intel a Flag, each tent a Command Post, KotH's hill and TC's territories Checkpoints. Their ids are fixed: 0x7FFF0000 + 0 team 1's intel, 1 team 2's, 2 team 1's tent, 3 team 2's, 4 the hill, 5 + i territory i. A carried intel has its trajectory's parent set to the carrier. The server sends the objective's Entity Update before the Game Mode State that goes with it.

Babel is sent as ctf. A client that does not know a mode shows the scores.

You report hits; the server decides damage. Our server refuses a gun hit whose fire position is more than 4 blocks from the shooter's eye, whose hit position is more than 3 blocks (plus lag tolerance) from the target, or whose line crosses a solid block. A melee hit is damage type Melee (4).

Hit Terrain

Client -> Server

InfoValue
Packet ID91
Total sizevariable
Field NameField TypeNotes
BlockBlock Coordthe cell hit
Damage TypeUint85 Dig, 4 Melee, 7..9 a gun
Fire PositionVec3
Hit PositionVec3

The spade's primary is Melee (destroy one block), its secondary Dig (the block and the ones above and below). A gun's hit is Weapon1..Weapon3; the slot is not checked for a block.

Our server keeps block health: a gun sends a Hit Terrain for every pellet that meets a block, and the server subtracts the weapon's damage (rifle 50, SMG 34, shotgun 20 a pellet, revolver 34) from the cell's 100. At 100 the block breaks; below it the cell goes out in the tick's Terrain Update as a solid cell with health 100 - damage — draw the crack. A crack heals 10 s after its last hit. The spade still counts on the client and sends only the hit that breaks the block.

Minimum Client

  1. ENet with 2 channels and the 1.0 connect data (or WebRTC), ignoring unknown ids.
  2. The primitive codec with the strict decoder rules.
  3. Initiate Connection with "WorldOfSpades 1.0" and Map Quality = 0, so you only need the VXL loader; certificates with isValid = 0.
  4. The map: header, fragments, final, decode, apply the kept terrain edits, acknowledge.
  5. Game State Final, Entity Update, Player Update, Player Remove, Entity Remove with the delta rule, the trajectory and its compact form.
  6. join <team> <weapon>, read local-player, then send Client Side Entity Update at 30 Hz.
  7. Hit Entity, Hit Terrain, Damage, Entity Die.
  8. Build Block, Build Line, Throw Grenade, Chat Message, Chat Broadcast, Terrain Update.
  9. Game Mode State for CTF, plus the Flag and Command Post entities.

Then ngmap, classes, perks, the match summary.

Implementation Notes

  1. Masks are not self-describing. One unknown bit means the packet cannot be decoded; reject it.
  2. Field order is not bit order in entity and player items.
  3. Terrain Update is R,G,B; every other colour is B,G,R.
  4. Compact trajectory z rounds up (toward the sky). Rounding to nearest puts a standing body inside the floor and the client's step-up makes every body bob.
  5. Ignore Entity Update parts for your own entity unless forced or Create, or you fight your own prediction.
  6. Send the update before the action. A hit or a build without a preceding input report is refused.
  7. Check the end before reading Entity Die's damage info.
  8. Unknown packet ids and map keys are ignored; unknown mask bits are errors.
  9. The server may restart the transfer at any time; drop the world, take the new map, join again.
  10. A Map Data Acknowledge is mandatory after decoding.
  11. map-format decides the decoder, not the quality you asked for.
  12. A WebRTC message over 16 KB is refused.
  13. Text is UTF-8; there is no CP437 in 1.0.
