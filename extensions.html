Extensions

This page documents the packet extensions of the 0.75 protocol: how a server and a client agree on one, the id registry, and the extensions our server speaks. The reference specification is zerospades/aosprotocol.

Overview

Every extension has a unique id, decided when it is first registered. There are two kinds:

TypePurposeExtension id range
HAS_PACKETSintroduces new packets0-191
PACKETLESSchanges existing packets or is only announced192-255

An extension with packets is reached by one legacy packet id equal to 64 + extension id. PACKETLESS extensions have no packet of their own.

Each extension packet carries one extra byte after the packet id: a sub packet id, used to have several packets per extension. It is always there, even when the extension needs only one packet.

Field NameField TypeNotes
Packet IDUint864 + extension id
Sub Packet IDUint80-255
DataUint8 arraythe sub packet's data

Ext Info

Client <-> Server

InfoValue
Packet ID60
Total size2 + 2 * n
Field NameField TypeNotes
CountUint8the number of entries that follow
EntriesExt Info Entry x count

An entry:

Field NameField TypeNotes
Extension IDUint8see the registry
VersionUint8at least 1; our server sends 1

The aosprotocol page words Count as "length, length+1 entries will follow". Our server writes and our client reads the entry count, with no +1. A client reading a server it does not know should treat the field as a count; if the first entry is not a known extension id and count - 1 entries parse cleanly to the end of the packet, the other wording was meant.

Protocol Flow

The server must send an Ext Info on connect (our server sends it right after State Data). The client stores the list and must reply with an Ext Info naming the extensions it supports.

The reply is the intersection: never name an extension the server did not offer, and never one you do not implement. An extension's packets go only to clients that agreed to it. A server sends nothing of a PACKETLESS extension; the agreement alone changes how it writes existing packets.

Player Properties

Server -> Client — extension 0x00, packet 64, sub 0

Field NameField TypeNotes
SubUint80
Player IDUint8
HealthUint80 for an enemy
BlocksUint80 for an enemy
GrenadesUint80 for an enemy
MagazineUint8
ReserveUint8
ScoreUint32kills plus score

Sent when a value changes, at most every 100 ms per player. A client keeps the ammo and score of everyone (the ammo decides whether another player's shot is drawn) but the health, blocks and grenades of its own player only.

Damage Markers

Server -> Client — extension 0x20, packet 96

Sub 0 is a damage marker: the attacker is told the victim and the amount; the client draws a hit marker, and a number rises over the victim. The exact fields are in the aosprotocol specification.

Teamplay

Client <-> Server — extension 0x30, packet 112

SubNameDirectionPurpose
0ConfigServer -> Clientwhat the server allows
1Pingbotha mark for the team
2ESP MarkServer -> Clienta spot shown through walls

Config:

Field NameField TypeNotes
SubUint80
FlagsUint8bit 0 teammate ESP, bit 1 pings, bit 2 compass
North XFloatthe map direction the client calls north
North YFloata zero or NaN means the map's top

A ping carries its position, life in seconds, colour, label and surfaces (world, map, compass); an ESP mark carries a target, life, whether to show the name, colour and label. The layouts are in the specification. Our server sends the server's own pings as player 255.

Pie Menu

Server -> Client — extension 0x31, packet 113

The server defines the quick-chat rings: a menu id, the contexts it applies to (block, teammate, enemy, sky, spectator, dead) and the slices with their text. A menu is parsed whole or refused. The layout is in the specification.

Flashlight

Client <-> Server — extension 0x32, packet 114

SubNameDirectionPurpose
0Lightbotha player's light on or off
1Light StateServer -> Clientone bit per player id
2Light ConfigServer -> Clientthe beam

Light:

Field NameField TypeNotes
SubUint80
Player IDUint8
OnUint80 or 1

A client sends Light to ask; the server relays the accepted request to every client that agreed, the owner included (a client draws only a light the server switched on). A light goes off silently on Create Player, Kill Action, Player Left and a new map: no packet, every client clears it itself.

Light State is [114, 1, bitmask...], one bit per player id, low bit first.

Daytime and Weather

Server -> Client — extension 0x33, packet 115

Field NameField TypeNotes
SubUint80
TimeUint160 night, 720 noon; other values are the day
ReservedUint8 x 4the weather in the draft; version 1 has a day and a night

The server sends it after the agreement and after every map. A client that agreed and got no Sky yet draws the night: with Time 0 the fog and the sky are black, and the flashlights are the only light. A new server starts by day.

Player Outfit

Server -> Client — extension 0x35, packet 117

A draft of the aosprotocol specification:

SubNameFields
0Set Outfitplayer, outfit, colour (0 team 1, 1 team 2, 255 its own)
1Team Outfitsteam, outfit pairs

Outfits: 0 soldier, 7 miner, 64 zombie, 255 the team's outfit. Cosmetic only. A player's outfit is reset when it leaves and at every map.

Player Limit

PACKETLESS — extension 0xC0

Announced through Ext Info only: the number of players the server accepts (the World Update's slot count). Nothing else is sent.

Message Types

PACKETLESS — extension 0xC1

A client that agreed may receive Chat Message types 3 (big), 4 (info), 5 (warning) and 6 (error); the others get type 2. Show 3..6 as popups.

Kick Reason

PACKETLESS — extension 0xC2

A system Chat Message from player 255 sent just before a disconnect is the kick text. Let it leave the ENet queue before disconnecting (enet_peer_disconnect_later, not enet_peer_disconnect).

UTF-8 Chat

Not an extension: a chat line or name beginning with byte 0xFF and valid UTF-8 after it is UTF-8. A client announces that it reads it through the extended version answer's feature bit 0 (below), and only then sends 0xFF lines itself.

Extra Packets

After a plain Version Send (34) a server may ask for more, once a connection:

Handshake Init

Server -> Client

InfoValue
Packet ID31
Total size5 bytes

Answer with the same four bytes (packet 32).

Extended Version Get

Server -> Client

InfoValue
Packet ID33
Total size1 + n

The bytes after the id are the property ids the server asks for. Answer with Existing Player (9) whose first byte is 'x' (0x78), then per property id, length, payload, one packet per property, each repeating the ones before.

IdMeaningPayload
0applicatione.g. BetterSpades 0.1.5
1languagee.g. en_us, pt_br
2feature flagsbit 0: reads UTF-8 chat

An unknown id gets an empty payload.
